# OOD observability in PyTorch

A local teaching example, tested on Python 3.12 / torch 2.4.1 / CPU.
No network requests, dataset downloads, labeling service or deployment.
Installing PyTorch requires access to a package registry unless already cached.

## Run

From this extracted directory:

    python3.12 -m venv .venv
    source .venv/bin/activate
    python -m pip install -r requirements.txt
    python -m unittest -v
    python demo.py

Windows: use `.venv\Scripts\activate` instead of `source`.

The demo creates a two-class neural network. It uses independent synthetic
training, ID calibration, old-domain test, reviewed new-domain training and
new-domain test data. The new domain shifts the second coordinate by five.
Labels are generated by a synthetic oracle, never by the network's predictions.
Three separate monitoring windows automatically trigger candidate training when
label readiness and the data contract pass. Original training data is replayed.

Outputs in the current directory:
- output/candidate.pt: model + freshly fitted/calibrated detector state dicts
- output/evaluation.json: paired point-estimate accuracies and example gate

This is a candidate, not a deployed model. The gate may pass or fail; neither
result changes any serving service. Results can differ across environments.
Loading an artifact you created yourself:

    bundle = torch.load("output/candidate.pt", map_location="cpu", weights_only=True)
    model = Classifier()
    model.load_state_dict(bundle["model"])
    detector = ClassDistance(2, 12)
    detector.load_state_dict(bundle["detector"])
    model.eval()
    detector.eval()

Import Classifier from demo and ClassDistance from ood first. Validate bundle,
architecture, preprocessing and schema versions before serving. Never mix a
model with a detector fitted on a different embedding space.

## What is implemented

- Per-class means with tied diagonal within-class variance, shrinkage and floor
- Independent ID quantile calibration; scores strictly above threshold flagged
- Input shape/non-finite checks; minimum class support
- Persistent non-overlapping windows, minimum volume, cooldown and label gate
- Automatic candidate training, replay, separate evaluation and bundle saving
- Six tests covering detector invariants, state, validation and trigger gates

## What you must add for a service

The in-memory Trigger assumes completed, ordered, non-overlapping windows.
Persist its state and window IDs. Use one transactional writer per policy/slice.
A scheduler should finalize windows with late-event watermarks, update the state
and insert a unique outbox job keyed by model/policy/dataset-manifest hash.
Workers need leases, bounded retries, resource limits and an idempotent artifact
path. Commit completion only after artifacts and evaluation are durable.

Replace synthetic labels with independently reviewed, provenance-tracked data.
The ready-label count must belong to the exact dataset, slice and period claimed
by the job. A boolean contract flag stands in for actual schema, validity,
label-quality and leakage checks. Split related examples by group/time before
training. Keep old/new test sets separate and untouched. Keep a random traffic
audit sample, not only flagged examples. Control raw-data access and retention.

The example uses accuracy point estimates and arbitrary 1-point/2-point gates.
Choose cost/slice/calibration/latency budgets in advance and account for sampling
uncertainty. Evaluate OOD detection separately, including failure cases. Add
shadow/canary rollout, outcome monitoring and rollback of an atomic bundle.
Refit/recalibrate a detector for every changed model using independent approved
calibration data. Newly supported classes require explicit schema/model changes.

The detector assumes diagonal, roughly unimodal class features. It can miss
unfamiliar inputs that map to familiar features and cannot detect pure label-
relationship changes from inputs alone. It is not the full Lee et al. method.
No production reliability or statistical false-alarm guarantee is implied.
